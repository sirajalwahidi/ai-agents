What "semantic" means when a machine searches

Two ideas underneath Homework 2's semantic search: turning text into a vector, and measuring how similar two vectors are.

Homework 1's Database Read Expert only understood exact spelling — ask about 'MSU' and it generates WHERE name = 'MSU', which matches nothing, because the row is stored as 'Michigan State University'. Homework 2 fixes this with two building blocks: embeddings, which turn text into numbers that capture meaning, and cosine similarity, which measures how close two of those number-lists are. This note walks through both, using the real numbers your own code produced.

1A vector is a list of numbers that stands in for meaning

An embedding is what you get when you feed a piece of text into a model trained to represent meaning numerically. The model returns a fixed-length list of floats — for the model this homework uses, openai/text-embedding-3-small, that list has exactly 1536 numbers, regardless of whether the input text was one word or one paragraph:

flask_app/utils/embeddings.py

generate_embedding("Michigan State University")
  → [0.0113, -0.0271, 0.0042, ..., 0.0089]   # 1536 numbers

generate_embedding("MSU")
  → [0.0119, -0.0258, 0.0039, ..., 0.0095]   # 1536 numbers, very close to the above

Nothing about those two input strings overlaps character-for-character. But because the model was trained on how language is actually used — and "MSU" and "Michigan State University" show up in near-identical contexts across huge amounts of text — the two output vectors land close to each other in that 1536-dimensional space. That closeness is the thing semantic search exploits. A vector by itself is just a list of numbers; it becomes useful the moment you can ask "how close is this one to that one?"

2"Close" means the angle between two vectors, not the distance

It's tempting to picture embeddings as points on a map, where "close" means a short distance between them. That's not quite what these models are compared by. What matters is cosine similarity — not how far apart two vectors' tips are, but how similar their directions are, measured as the angle between them from the origin:

The formula behind that angle is the dot product of the two vectors, divided by the product of their lengths — which cancels out length entirely and leaves only direction:

flask_app/utils/database.py — _cosineSimilarity

dot_product = sum(a * b for a, b in zip(vector_a, vector_b))
magnitude_a = sqrt(sum(a * a for a in vector_a))
magnitude_b = sqrt(sum(b * b for b in vector_b))
similarity  = dot_product / (magnitude_a * magnitude_b)

The result always falls between −1 (pointing in exactly opposite directions — opposite meaning) and 1 (pointing in exactly the same direction — identical meaning). Dividing by both magnitudes is what makes this a comparison of meaning rather than of length: a long paragraph about Python and a short phrase about Python should score as similar, even though their raw vectors have very different magnitudes.

3Semantic search: rank every row by that score

Semantic search is what you get by repeating that comparison across an entire table and keeping the highest scores. Asking "What AI skills do I have?" against the skills table produced exactly this, using your real seeded data:

Notice that none of the matched skill names contain the word "AI" at all — the ranking comes entirely from meaning, not shared vocabulary. This is the mechanism behind your Database Semantic Search Expert — a dedicated expert the Orchestrator routes to instead of the Database Read Expert whenever a request can't be answered by exact SQL matching, which then hands the table and search text to db.semanticSearch() to do the ranking shown above.

4Two different moments an embedding gets computed

There's a design choice hiding in "compare against every row": when do those row-level vectors get computed? Computing one on every single question would be needlessly expensive, since a row's embedding only changes when the row's text does. So the work is split into two separate moments that only meet at comparison time:

In one sentence

An embedding turns text into a direction in a 1536-number space; cosine similarity measures how closely two directions match; semantic search is just doing that comparison against every row and keeping the closest ones — computed once per row when it's written, and once per question when it's asked.
