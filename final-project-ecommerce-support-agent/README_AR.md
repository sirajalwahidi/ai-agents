## 📌 1. نظرة عامة على المشروع

**وكيل دعم التجارة الإلكترونية الذكي** هو نظام مستقل متعدد الوكلاء مصمم لخدمة عملاء المتاجر الإلكترونية. يعالج النظام استفسارات العملاء عن حالة الطلبات وتتبع الشحنات وتحديثات الشحن ويجيب عنها بدقة عالية، مع الاعتماد على صلاحيات مرتبطة بجلسة العميل وطبقات حماية متعددة لحفظ بياناته.

* **الفئة المستهدفة:** أصحاب المتاجر الإلكترونية، وفرق دعم العملاء، وأقسام المساندة التقنية.
* **الهدف الأساسي:** بناء نظام وكيل ذكي بمستوى إنتاجي يجمع بين فهم اللغة الطبيعية (LLM)، واستدعاء الدوال المنمّطة (Typed Function Calling)، والوعي الديناميكي بمخطط قاعدة البيانات، وصلاحيات الجلسة، ومبادئ التصميم المتمحور حول الإنسان.

---

## 🏗️ 2. معمارية الوكيل وطبقات الحماية

يلتزم المشروع بالصيغة الأساسية لوكيل الذكاء الاصطناعي:

$$\text{AI Agent} = \text{LLM} + \text{Planning} + \text{Tooling}$$

يتكوّن النظام من **5 مكونات متخصصة** تحيط بها طبقات حماية وتحقق صارمة:

1. **الوكيل المنسّق (Orchestrator Agent):** يحلل مدخلات العميل، ويوحّد اللغة والأرقام، ويكتشف النية، ويوجّه الطلبات إلى أدوات محددة ومنمّطة لكل مجال.
2. **أدوات القراءة المنمّطة (`get_order_status`، `track_shipment`):** واجهات قراءة فقط ذات معاملات محددة. تعمل القراءة عبر اتصال SQLite للقراءة فقط (الوضع `mode=ro` في الرابط) مع الأمر `PRAGMA query_only = ON`، ومصرّح وصول في SQLite يمنع الوصول إلى الجداول والأعمدة غير المسموحة. ويُربط `customer_id` بجلسة العميل الموثّقة، ولا يختاره النموذج أبداً.
3. **أدوات الكتابة المنمّطة بتأكيد على مرحلتين (`cancel_order`، `update_shipping_address`):** تجهّز الإجراءات التي تغيّر البيانات عبر بروتوكول من مرحلتين (اقتراح ← رمز تأكيد من العميل ← تنفيذ)، فيُفرض تدخّل الإنسان في الكود نفسه وليس في التعليمات النصية فقط. ويعيد التنفيذ التحقق من ملكية الطلب وحالته لحظة الحفظ.
4. **حلقة التحقق من الاستناد (Grounding Verification Loop):** آلية نقد ذاتي ثانوية تفحص مسودات الردود مقابل مخرجات الأدوات الخام، لاكتشاف الادعاءات غير المدعومة وتقليلها.
5. **التصعيد إلى موظف بشري (`create_support_ticket`):** يوقف استقلالية الوكيل ويسجّل تذكرة منظمة للدعم البشري عند انخفاض ثقة النموذج، أو المطالبات المالية المعقدة، أو طلب العميل الصريح.

## 🛠️ 4. التقنيات المستخدمة وأدوات الحماية

* **لغة البرمجة:** Python 3.10+
* **نموذج اللغة الرئيسي:** واجهة Google Gemini API (حزمة `google-genai` الإصدار 1.0 فما فوق)
* **استدعاء الأدوات:** استدعاء دوال أصلي بمعاملات محددة
* **قاعدة البيانات والحماية:** SQLite3 (`ecommerce.db`) مع وضع القراءة فقط عبر الرابط، و`PRAGMA query_only`، ومصرّح وصول SQLite، وصلاحيات `customer_id` المرتبطة بالجلسة.
* **أدوات المدخلات:** موحّد مخصص للأرقام العربية الهندية، ومعالجة للتعليمات متعددة اللغات.
* **واجهة المستخدم:** واجهة سطر أوامر تفاعلية (CLI) تعرض مسار تفكير الوكيل لحظياً.
* **إدارة البيئة:** `python-dotenv` لحماية مفتاح الواجهة البرمجية.

## 🗄️ 6. مخطط قاعدة البيانات (`ecommerce.db`)

تتكوّن قاعدة البيانات العلائقية من 4 جداول مُطبَّعة:

* **`customers`**: سجلات هوية العملاء (`customer_id`، `name`، `email`، `phone`).
* **`orders`**: دورة حياة الطلب (`order_id`، `customer_id`، `order_date`، `status`، `total_amount`، `shipping_address`).
* **`shipments`**: بيانات الشحن واللوجستيات (`tracking_number`، `order_id`، `carrier`، `current_location`، `estimated_delivery`، `status`).
* **`support_tickets`**: حالات سير عمل التصعيد البشري (`ticket_id`، `order_id`، و`status` بإحدى القيم: `bot_active` أو `escalated_to_human` أو `resolved`).

## 📊 7. مقاييس التقييم والنتائج التجريبية

جرى قياس أداء الوكيل وفق معايير قياسية باستخدام سيناريوهات اختبار كاملة من البداية إلى النهاية في بيئة التشغيل:

| المقياس | التعريف | المعيار / النتيجة التجريبية | الحالة / ملاحظات |
| :--- | :--- | :--- | :--- |
| **معدل نجاح المهام (TSR)** | نسبة استفسارات العملاء المحلولة بدقة بردود مسندة إلى الوقائع ودون أي انتهاك أمني. | **100%** | اجتاز استعلامات القراءة، واختبارات حدود الوصول بين الحسابات (IDOR)، وتتبع الشحنات، وحجب الإلغاء في الحالات غير المسموحة. |
| **معدل التدخل البشري (HIR)** | نسبة التذاكر المعقدة أو المتنازع عليها المصعّدة إلى الدعم البشري مقابل التي حلّها الوكيل ذاتياً. | **20%** | سيناريو واحد من 5 سيناريوهات أساسية أدى إلى التصعيد (أُنشئت التذكرة رقم 3 لبلاغ نقص عنصر في الطلب). |
| **زمن الإنجاز (TTC)** | متوسط الزمن اللازم لجلب بيانات متحقق منها وتنفيذ الأدوات وصياغة ردود مسندة. | **من 1.8 إلى 2.5 ثانية** | استجابة سريعة بفضل أدوات SQLite المباشرة واستدلال نموذج Gemini Flash. |

### 🛡️ التحقق من الأمان وسلامة البيانات

* **الحماية من IDOR:** جرى التحقق من أن الاستعلامات عبر الحسابات (مثل وصول العميل رقم 1 إلى الطلب رقم 3) تُرفض بصرامة عند طبقة قاعدة البيانات.
* **بروتوكول المرحلتين:** جرى التحقق من أن تعديل الحالة (الإلغاء وتحديث العنوان) يتطلب رموز تأكيد صحيحة، وأن محاولات التنفيذ غير المصرّح بها أو برموز خاطئة تُحجب بنجاح.
* **فرض منطق الحالة:** جرى التحقق من أن حالات الطلب غير القابلة للإلغاء (مثل `delivered` و`shipped`) توقف التعديل تلقائياً وتعرض التصعيد إلى موظف بشري.

## 🔮 10. خارطة الطريق المستقبلية والمرحلة الثانية (توسعة النسخة الإنتاجية الأولية)

بينما أنجزت **المرحلة الأولى** إثبات مفهوم آمناً بواجهة سطر أوامر وجلسة واحدة، صُمّمت الترقيات المعمارية التالية لنقل نظام الوكيل إلى حل مؤسسي موزّع ومتعدد المستأجرين:

### 1️⃣ إدارة الحالة والذاكرة الموزّعة (التكامل مع Redis)

* **القيد الحالي:** تُخزَّن رموز التأكيد الخاصة بأدوات المرحلتين في ذاكرة العملية المحلية (القاموس `PENDING_CONFIRMATIONS`).
* **ترقية المرحلة الثانية:** نقل رموز الإجراءات المعلّقة وحالات الجلسات إلى **ذاكرة Redis المؤقتة** مع مدة صلاحية (TTL). وهذا يتيح التوسّع الأفقي عبر عدة عمليات تشغيل دون فقدان حالات التأكيد.

### 2️⃣ قاعدة بيانات علائقية مؤسسية (الانتقال إلى PostgreSQL)

* **القيد الحالي:** يدير SQLite التزامن عبر قفل على مستوى الملف، وهو مناسب للتحقق المحلي.
* **ترقية المرحلة الثانية:** الانتقال إلى **PostgreSQL** مع تجميع الاتصالات (Connection Pooling) لدعم عمليات الكتابة المتزامنة، مثل تحديث العناوين وإنشاء التذاكر في وقت واحد من مئات جلسات العملاء النشطة.

### 3️⃣ لوحة دعم بشري لحظية (WebSockets / Flask-SocketIO)

* **القيد الحالي:** تُحفظ التذاكر المصعّدة في الجدول `support_tickets` وتُسجَّل في طرفية الأوامر.
* **ترقية المرحلة الثانية:** بناء واجهة ويب رسومية تضم أداة محادثة مباشرة للعملاء ولوحة تذاكر لحظية لموظفي الدعم، باستخدام **WebSockets** لتنبيهات التصعيد الفورية والاستلام المباشر للمحادثة.

### 4️⃣ التكامل اللوجستي المباشر والمعالجة متعددة الوسائط

* **القيد الحالي:** تجلب استعلامات الشحن بيانات شحنات تجريبية من الجدول `shipments`.
* **ترقية المرحلة الثانية:** دمج خطافات الويب (Webhooks) عبر REST API لشركات الشحن الخارجية (مثل Aramex وDHL)، وتنفيذ التعرّف الضوئي متعدد الوسائط (OCR) للتحقق من فواتير العملاء وإيصالاتهم عند طلبات الإرجاع.
